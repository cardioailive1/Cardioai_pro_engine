2. System Overview

The platform has five layers. Users reach it through web and mobile applications; an application layer handles authentication, tenancy and APIs; the agent pipeline orchestrates analysis; AI models produce clinical outputs; and integrations connect to health system and payer data.

3. The 15-Agent Orchestration Pipeline

Each agent performs one step and passes structured output to the next, so individual steps can be tested, replaced and audited separately. The pipeline has been tested end to end. The table groups the agents by stage; the CTO will complete the agent-level detail.

StageAgentsFunctionStatus
IntakeingestionReceive documents, claims files, clinical records and device data; validate formatLive
Normalizationquality, fhir, dicom (imaging only)Parse X12 837/834; map clinical data to internal schema; (FHIR mapping handled by FHIRAgent — built and tested)Live (X12 via QualityAgent/FHIRAgent); DICOM metadata/pixel extraction live (DICOMAgent) — PACS query/retrieve not yet built
Clinical analysisintake, longitudinal, fusionExtract features from ECG, echo, labs and historyLive — PatientIntakeAgent appends the reading to history; LongitudinalAgent computes trend statistics (baseline deviation, slope, volatility); FusionAgent combines the current score with the trend (and imaging features, where present) into one fused assessment
Risk scoringinferenceGenerate cardiovascular risk outputsPlaceholder heuristic; validated model to replace it
Explanationdiagnostic, automationProduce reasons and evidence behind each output for the clinicianLive — DiagnosticAgent turns the (fused) score into a diagnosis, ICD-10 candidate and confidence; AutomationTierAgent sets the automation tier (auto-escalate / clinician recommendation / log only). Diagnoses are limited to a generic abnormal-finding code today, which keeps the top automation tier structurally unreachable from this pipeline by design
Payer analyticsclaims_aggregatorPopulation stratification and claims-based analyticsLive — runs only on the claims pipeline, rolling each record into the payer population report
Reporting and auditreport, alert, continuum, registryGenerate reports; log every step for traceabilityLive — ClinicalReportAgent builds the clinical report; AlertAgent raises high-risk alerts; ContinuumAgent updates the patient’s care-continuum stage; PatientRegistryAgent persists the result. The orchestrator also logs every agent hop to an in-memory event log (Section 7, live dashboard only) AND writes one persisted audit row per completed/failed pipeline task to Postgres (auth/audit.py) — see Section 7

Orchestration framework: a custom Python async orchestrator (CentralOrchestrator) dispatches ordered agent lists in-process, not a third-party agent framework. Agent models: no third-party or external AI/LLM API is called by the live pipeline today; ModelRegistry runs placeholder heuristics in-process pending trained model weights (Section 6). Inter-agent messaging: direct in-process function calls coordinated by the orchestrator; each agent’s output becomes the next agent’s input; no message queue or network hop between agents. No third-party AI service is called by the agent pipeline today, so no AI-subprocessor BAA is currently needed; if one is added later, it must sign a BAA with zero-retention terms before processing any PHI (see the HIPAA and Security packet).

7. Security Architecture (Summary)

Data is encrypted in transit via TLS terminated at the hosting provider’s edge (Render) for inbound traffic; this app’s own outbound calls (IoMT client, integrations/iomt_client.py) pin a TLS 1.2 minimum in code (ssl.SSLContext). Encryption at rest: Data Room documents are encrypted at the application layer (Fernet/AES-128, encryption.py) before they reach either storage backend (local disk or Cloudflare R2), independent of provider, verified tamper-evident (an altered ciphertext fails to decrypt rather than returning corrupted plaintext). Render-managed PostgreSQL (users, organizations, audit log, no PHI stored there) relies on the provider’s managed-disk encryption. Audit logging is now two-layered: agent pipeline hops still log to the in-memory, 200-event dashboard trace (not persisted, unchanged), and a separate, persisted Postgres audit log (auth/audit.py) now records user actions (login, logout, signup, approval/rejection/disabling) and one row per pipeline task completion/failure, queryable via GET /api/audit/events (admin-only) and retained for 400 days by default, purged on a daily scheduled job (render.yaml).
